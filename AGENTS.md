# Agent guidance

DynLight ports Henry de Jongh's Unity package "Dynamic Lighting" to a standalone Bevy 0.20 crate.

- **Bake time:** baked per-texel shadow bits per (triangle, light).
- **Runtime:** live evaluation of light color, intensity, effects and types in our own WESL material.

`PLAN.md` is the design and milestone record. Read it before starting any milestone work. This file holds the rules for working in the repo.

## Hard rules

1. **No Bevy lights.**
   - Never spawn, read or depend on `PointLight`, `SpotLight`, `DirectionalLight`, `RectLight`, `AmbientLight`, `EnvironmentMapLight`, `GeneratedEnvironmentMapLight`, `Skybox`, `Atmosphere`, irradiance volumes, `Lightmap`, Bevy shadow maps or Solari. Suns and skies are our own light types and passes.
   - Never import `bevy_pbr` lighting, shadow or clustering shader modules (`pbr_functions`, `lighting`, `shadows`, `shadow_sampling`, `clustered_forward`, `fog`, or the light data in `mesh_view_bindings`).
   - `StandardMaterial` may only be *read* by `gltf_import` in order to convert it.
   - No vendored or patched `bevy_pbr`, and no `[patch.crates-io]` for Bevy crates.
   - What we may use from Bevy is the non-lighting infrastructure: ECS, assets, the `Material` trait and mesh pipeline, `ShaderBuffer`, `MeshTag`, `GpuComponentArrayBuffer`, `mesh_functions`, view uniforms, the prepass, the `Core3d` schedule, and gizmos.
2. **No Unity libraries or engine behavior.**
   - Do not reimplement or bit-match `UnityEngine.Random` (Xorshift128 / `InitState`), `Mathf.PerlinNoise`, `Unity.Mathematics`, physics or `RaycastCommand`, Unity shader includes and macros (`UnityCG.cginc`, `UnityObjectToClipPos`, `unity_*`, `_Time`, …), or Unity camera rendering.
   - Do not add tests or fixtures generated by running Unity.
   - Use our own RNG and noise, `glam`, our BVH ray tracer, `rayon`, and Bevy APIs instead.
3. **Henry's code is MIT and may be ported directly.**
   - Keep his in-file copyright headers verbatim where they exist (e.g. the angular distance-cube filter).
   - His full MIT notice lives in `LICENSES/`.
   - Snippets inside his package that are not his get special handling:
     - BRDF code reproducing LearnOpenGL (CC BY-NC): rewrite from the published formulas.
     - The Shadertoy `rand` (CC BY-NC-SA): replace with our hash.
     - SmoShaders Gaussian blur (MIT, © 2019 Daniel Ilett): port it, and keep its notice in `LICENSES/`.
4. **The user's bevyout port (`DynamicLightsPort` branch) may be reused freely.**
   - Delete its Unity parity code: `unity_random.rs`, the Perlin code in `unity_math.rs`, `reference_unity/`, and `tests/golden/`.
   - Delete its Bevy-light code: `shadow_proxy.rs` and the patched-`bevy_pbr` forward hook.
5. **Max 400 lines per file** (see "File length").
6. **Vertical Slice Architecture** (see next section).

## Architecture: Vertical Slice Architecture

The crate is organized by feature, not by technical layer. A slice owns its full path: authoring data, pure logic, ECS systems, render-world code, shaders and tests. Do not create global `systems/`, `components/`, `render/` or `shaders/` folders.

```
src/
  lib.rs                 DynamicLightingPlugin: adds slice plugins, nothing else
  shared/                small kernel used by >= 2 slices: BakeId + stable ordering, GPU light ABI,
                         math helpers, WESL `types` / `math` / `bindings` modules
  light/                 DynamicLight authoring, enums, presets, light buffer, realtime budget, moved lights
  light_clusters/        per-cell realtime light lists over the realtime-selection camera, clusters.wesl
  effects/               intensity effects, noise, RNG, fixed timestep
  surface/               DynLitMaterial (diffuse / metallic / unlit), prepass, BRDF, lighting composition WESL
  bake/                  CPU baker (light BVH, occluder BVH, triangle builder, rays, seams, bounce,
                         distance cubes, sun maps), .dynlight format writer + reader, BakeRequest + progress
  baked_lighting/        .dynlight asset loading, triangle / aux buffers, receiver records via MeshTag,
                         primitive-index path + triangle-ID fallback, stale-bake detection, triangles.wesl
  dynamic_geometry/      light BVH, distance cubes and sun maps at runtime, distance_cubes.wesl, sun_map.wesl
  realtime_shadows/      VSM shadow cubemap pass (Core3d systems), vsm.wesl, blur
  cookies/               cookie texture array
  environment/           sky light from an equirect image: CPU prefilter (SH9 + GGX cube), sky background pass
  fog/                   volumetric fog pass
  gltf_import/           glTF extras -> DynamicLight, StandardMaterial -> DynLitMaterial
  debug/                 gizmos, debug views, diagnostics
examples/  tests/  benches/  assets/  LICENSES/  docs/
```

### Slice template

```
src/<slice>/
  mod.rs                 public API only: the slice's Plugin, re-exports, SystemSets (keep it short)
  <logic>.rs             pure logic: std, serde, bevy::math (glam), bevy::color and the slice's own data
                         types; no queries, Commands, resources, render or asset types
  systems.rs             main-world ECS systems (split further when large)
  render/ or render.rs   extract / prepare / Core3d systems
  shaders/*.wesl         loaded with `load_shader_library!` in `Plugin::finish`, behind
                         `shared::shaders_available` so headless apps work; importable as
                         `dynlight::<slice>::shaders::<name>`
  mirror.rs              CPU reference of the slice's shader math, used by tests
  tests.rs or tests/     unit tests that don't fit inline
```

### Slice rules

- **Dependencies:**
  - A slice may use `shared/` and another slice's public API from its `mod.rs`.
  - It must never reach into another slice's private files.
  - No dependency cycles between slices.
  - Shader imports follow the same rules.
- **`shared/` stays small.** Something moves there only once a second slice needs it. Never move code there just to escape the 400-line limit.
- **Pure logic and Bevy systems stay separate:**
  - Put decision logic (packing, effects, BVH, bake steps, budgets, culling decisions) in pure modules with unit tests.
  - Bevy systems stay thin: they query, call the pure logic, and write results.
- **`lib.rs`** only composes plugins. New features get a new slice with its own `Plugin`; don't grow an existing slice's scope.
- **The composition point:** `surface/` composes the per-slice shader modules into the lighting loop. Each slice exports its WESL functions; `surface/` calls them.

## File length

- **The limit:** every hand-written source file is at most **400 lines**, counted as physical lines (`wc -l`), including comments, blank lines and inline `#[cfg(test)]` modules.
- **Scope:**
  - Covered: `*.rs`, `*.wesl`, `*.wgsl` and `*.feature` under `src/`, `tests/`, `examples/`, `benches/` and `features/`.
  - Exempt: Markdown, `Cargo.lock`, and data fixtures.
- **How to split** when a file nears the limit:
  - Split by responsibility inside the slice (e.g. `bake/rays.rs`, `bake/seams.rs`). Never `part1.rs`/`part2.rs`.
  - Move large test modules to a sibling `tests.rs` or a `tests/` folder.
  - Move big constant tables into their own file.
  - Don't work around the limit with long lines; rustfmt defaults apply.
- **Files already over the limit:** ported sources that exceed 400 lines are split while porting.
  - Henry: `DynamicLighting.cginc` (1174), `DynamicLightManager.cs` (1621), `DynamicLightingTracer.cs` (1273).
  - bevyout: `render/gpu.rs` (801), `baker.rs` (926), `core/volumetric.rs` (519), `bevy_bridge/mod.rs` (504), `core/runtime.rs` (443).
- **Enforcement:** `tests/repo_hygiene.rs` fails on any file over 400 lines and on forbidden identifiers (Bevy light, sky and environment types, banned `bevy_pbr` modules, naga_oil syntax, `unity_random`, `PerlinNoise`, `1812433253`, `[patch.` in `Cargo.toml`). Extend it when you add a rule. The same line check by hand:

```bash
find src tests examples benches features -type f \( -name '*.rs' -o -name '*.wesl' -o -name '*.wgsl' -o -name '*.feature' \) \
  -exec wc -l {} + | awk '$2 != "total" && $1 > 400'
```

## Bevy 0.20 specifics

- **Check APIs against Bevy 0.20, not memory.** Use the docs.rs page for `bevy` 0.20.0 and the `v0.20.0` examples, especially `shader/storage_buffer.rs`, `shader/gpu_component_array_buffer.rs`, `shader_advanced/custom_post_processing.rs`, `render_depth_to_texture.rs` and `custom_render_phase.rs`.
- **Shaders are WESL (`.wesl`).**
  - Imports look like `import bevy_pbr::render::mesh_functions;`.
  - Conditionals use `@if(FLAG)`.
  - Integer defs are read as `constants::NAME`; the material group is `@group(constants::MATERIAL_BIND_GROUP)`.
  - No naga_oil syntax (`#import`, `#ifdef`, `#define_import_path`, `#{...}`).
- **Storage buffers:** `ShaderBuffer` (`bevy::render::storage`) copies raw bytemuck bytes, so padding is manual.
- **Render passes** are systems in the `Core3d` schedule (`Core3dSystems::{Prepass, MainPass, PostProcess}`), not render-graph nodes.
- **Errors:** fallible systems and loaders return `Result` and use `BevyError` `.context(...)`. Don't `unwrap` in runtime paths unless it guards a real invariant.
- **Change ticks:** use `#[component(summary_tick)]` on components that are queried with `Changed` often but change rarely.

## Porting conventions

- **Reference checkouts** (not part of this repo; never commit them): `C:\Users\V\Documents\dynlight-refs\DynamicLighting` (Henry) and `...\dynlight-refs\bevyout` (sparse checkout of `DynamicLightsPort`).
- **Provenance:** keep `docs/PORT_MAP.md` up to date, one row per ported file: our file, Henry's source file and line range, bevyout source, and status. Don't put provenance comments in code; the map is the record.
- **HLSL → WESL:** follow PLAN.md §7.2.
  - Explicit u32/i32/bool conversions.
  - No `x++` inside expressions.
  - Struct methods become free functions.
  - `mul(v, look_at)` is written as dot products.
  - `select` argument order is reversed from the ternary.
  - Rename `common`, and any parameters named `min`/`max`.
- **Coordinates:** Bevy is right-handed with −Z forward; Unity is left-handed with +Z forward.
  - Re-derive cube-face tables and lookup cubes. Don't copy them.
  - Spot `forward` is uploaded as `transform.back()`.
  - Negate `right` for cookies, rotor and disco.
- **Henry's quirks:** fix the bugs and keep the look-defining constants, as listed in PLAN.md §12. If you find a new quirk, add it there instead of deciding silently.

## GPU data rules

- **Struct definitions:** every GPU struct is `#[repr(C)]` + `bytemuck::{Pod, Zeroable}` in Rust, with a matching WESL struct.
- **Layout tests:** each GPU struct has a test asserting its size and every field offset. The light struct is 112 bytes; WGSL `vec3` aligns to 16, so check the field order.
- **ABI changes:** change the Rust struct, the WESL struct and the layout test in the same commit.
- **`.dynlight` format:** any change bumps the format version in `bake/format`. Loaders reject unknown versions with a clear error.
- **Upload frequency:** static bake data (triangles, aux, lookup cube) is uploaded once when the asset loads, never per frame. Per-frame writes are limited to the light buffer and the realtime lists.

## Bake determinism

- **Same output every time:** the same input must produce byte-identical output on any thread count.
- **Seeding:** seed the RNG per (mesh, light, texel, sample) with a stateless hash. Never use a global RNG.
- **Ordering:** order by `BakeId` and BVH order only. Never iterate a `HashMap`/`HashSet` into output.
- **Identity:** meshes and lights are matched to bake data by `BakeId` and a content hash. A mismatch falls back to the unbaked path and is reported in diagnostics; it is never silently reused.
- **No entity ids in output:** never derive anything that is saved or rendered (seeds, keys, ordering) from `Entity` ids. They shift whenever anything is spawned earlier, resources included, which changes the image. Use `BakeId` or `shared::NamePaths`.

## Testing

- **Pure logic:** unit tests. For shader math, write CPU mirrors in Rust and compare them with GPU readback at chosen pixels.
- **Fixtures:** synthetic only (e.g. plane + box occluder + light, with the analytic shadow footprint). No Unity output, and no third-party game data.
- **Bake tests:** determinism, light BVH query vs brute force, a round-trip of the triangle-word layout, and seam and padding cases.
- **Visual check:** `tests/gpu_examples.rs` runs the `gpu_check` example (GPU readback vs the CPU mirrors) and checks `lighting_test` screenshots. It needs a GPU, so it is ignored by default: run `cargo test --test gpu_examples -- --ignored` after touching shaders or render code.
- **Visual baselines:** `tests/gpu_baselines.rs` compares still frames of the examples (`--capture`) with `tests/baselines/*.png` using FLIP. Run `cargo test --test gpu_baselines -- --ignored --test-threads=1` after any change that could alter the image, including refactors and performance work.
  - A failure is a regression until shown otherwise: look at the error map in `target/tmp/baselines/`.
  - Re-bless (`DYNLIGHT_BLESS=1`) only for an intended change to the look. Look at every new image before committing it, and say in the commit message why the look changed.
  - Baselines are our own renders only, never Unity or third-party output. Keep them few and at 1280×720.
  - New features get a baseline view in an existing case or a new case.

## Build and verify

- **Dev aliases:** `.cargo/config.toml` has `check-dev`, `test-dev`, `run-dev` and `clippy-dev`, which enable the crate's `dev` feature (Bevy `dynamic_linking`). Use them for iteration only; release builds must not depend on the Bevy DLLs.
- **Before handing off, all of these must pass:**

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
# or the example covering the slice you touched; --frames exits, --screenshot saves an image to look at
cargo run --example lighting_test -- --frames 240 --screenshot screenshots/lighting_test.png
```

- **CI** (`.github/workflows/ci.yml`) also runs `cargo deny check` against `deny.toml`. Every ignored advisory there carries a reason and a removal condition.

## Logging

- **Library code:** use `tracing` macros (`info!`, `warn!`, `error!`). Never `println!`.
- **Bake progress and stats:** stable, grep-friendly prefixes, e.g. `dynlight bake: meshes N, texels N, rays N, ms N`.

## Git

- **Staging:** stage files explicitly by path; never `git add -A` or `git add .`.
- **Never commit:** reference checkouts, Unity-generated data, or large baked outputs. Small synthetic `.dynlight` fixtures under `tests/fixtures/` are fine.
- **Dependencies:** permissive licences only (MIT, Apache-2.0, Zlib, BSD), enforced by `cargo-deny` in CI.
